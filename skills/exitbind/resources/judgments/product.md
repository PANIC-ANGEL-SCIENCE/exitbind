# Product and external use

Use this reference when evaluating product readiness or designing an operator
experience. Start from the user, task, and observable value. Inspect how a
person discovers the capability, reaches a useful result, understands the
current state and permissions, recovers from an error, and returns later.
Consider access, accessibility, onboarding, credibility, cost, positioning,
distribution and retention only where they affect the decision.

Separate a promising concept from demonstrated usefulness and adoption. Name
the evidence and its population; distinguish direct human observations, public
reports, self-use and simulations. Do not invent demand or represent a proxy
as user testimony. Propose the smallest ethical observation that would change
the decision, within the authority and consent already provided.

For interface work, make state, authority, reversibility, uncertainty and the
next action legible. Specify information structure, interaction, user-visible
states, likely failure recovery and testable outcomes. Preserve established
user choices and distinguish inferred intent from an accepted requirement.
Give a sketch only when it clarifies the design. Design advice is not proof of
implementation, operational behavior, acceptance or release readiness.

## Public entry documentation

For a substantial README audit or revision, establish the requested audience,
the actual checkout and any in-scope local changes. Check important claims,
commands and examples against current source, package metadata, help and
appropriate evidence. A roadmap, badge, self-report or build result is not
evidence for an unrelated safety, compatibility or adoption claim. If a
supported path or evidence is unavailable, state the gap.

For an active product, give a new reader the useful outcome and one supported
first-success path, including material prerequisites, cost, data and authority
boundaries. Show how to recognize success and, where relevant, stop, recover,
update or remove the product; identify remaining data and credential revocation.
For an archived or superseded project, lead with its current state and supported
next action instead of presenting an obsolete install path as current. Mark
optional paths and unexercised instructions, and link to real detailed guidance
rather than exposing private operational information. An audit does not
authorize editing or publication.

## Research and fair comparisons

Frame the decision, target situation, plausible alternative and the observation
that would change the next action. Reuse existing evidence before collecting
more. When comparing a proposed path, use a competently applied baseline and
include setup, assistance, trust, switching and recurring costs on both sides.
Record source, context, date, assistance and contrary cases where known; repeated
copies of one report do not become independent participants. Protect consent
and retention boundaries, and distinguish an actual human report or observed
use from behavioral records, self-use, AI proxies and inference. Missing access
is not permission to invent a participant or substitute a simulated result.
For first-contact review, disclose what the reviewer saw and whether assistance
or prior context shaped the response; preserve the initial observation before
supplying additional explanations.
