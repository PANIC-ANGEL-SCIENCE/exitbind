# Develop the interface and inspect it at use size

Use for a new UI screen or substantial visual redesign. For a hero board or case study, begin with [portfolio presentation](portfolio-presentation.md), then apply this route to the embedded product. Keep task evidence outside the reusable pack.

## Establish task, content and boundaries

Name the user action, required states, actual language, viewport, deliverable and approved choices. Scope visual constraints separately to UI, content imagery and presentation. A static image, clickable prototype and working product are different outcomes. Preserve requirements, not a rejected designer-selected solution; for independent concepts, exclude prior generated geometry unless comparison/remake is authorized. Do not claim blindness after exposure.

Personally view relevant readable materials through [Discovery](discovery.md). Source titles, downloads and handoff descriptions are not pixel inspection. Apply [source roles](reference-roles.md): photographic subject, interface and presentation references can have different jobs. Resolve essential missing inputs before dependent production.

## Explore the product relationship

Start with real content and the action that makes this product useful. Build a small state strip or prototype when the interface idea is uncertain. A presentation or photographic relationship may need exploration alongside it; do not lock the entire board merely to finish states in order. Compare materially different relationships at comparable fidelity: how information is grouped, how selection changes space, how content and control share a frame, or how detail relates to its origin. A palette swap or new bottom-sheet contour alone is not a new interaction concept.

Map the user’s required actions to visible changes: initial state → action → changed content/control → next action → resulting state. Show the initial context when it is part of the request; do not start after the first action has already happened. Preserve selection and useful back context. For each promising direction, show its meaningful before/after and return or dismissal where relevant. Keep object identity, labels and primary action consistent. Explore visual form without inventing unsupported product behavior. A static transition is still only a proposal; test real behavior when implementation is in scope.

Do not reflexively reject layering, expressive controls or unusual density. Test the concrete reading, occlusion, target and recovery problem. Preserve an accessible stable route. A conventional pattern can win through suitability, but should not survive simply because it is the first default.

## Compose with actual assets and language

Use [visual methods](visual-methods.md), [typography](typography.md) and [interface craft](interface-craft.md) only as needed. Set actual text and images before locking geometry. Compare title/label silhouettes, crop anchors, grouping and state forms at intended size. Make the chosen expressive relationship visible in the product, not only in its logo or board background. A deliberately photo-led interface is valid if the photography and its placement carry the concept specifically.

Inspect the clean source photo before locating markers or selecting crop. Bind annotations to the displayed crop coordinate system. In a detail state, show the selected object's evidence, not merely the same appealing image. Keep texture, seams, hands and object edges intact where they matter. Authentic context does not justify poor photographic craft.

## Resolve shape and naming as product decisions

Carry explicit control silhouettes into actual states through [interface craft](interface-craft.md), not merely a border-radius token. Bind the requirement to its target controls; a requested capsule is not a global shape system. Check visible contour, label fit, action recognition and stable targets together.

Choose a consistent naming-language policy for the relevant content set. It may use one language, preserve proper names, or mix languages intentionally by role; English is not a default quality upgrade. Set real names before layout and compare glyph mass, baseline, line breaks, wrapping, truncation and hierarchy at product and delivery size. Do not translate official product names or invent attributes to make a board look consistent. Rerun all related states/pages after a name or language changes.

## Produce separable source

Prefer editable screen source with live text, meaningful layers and reusable original assets when precision, multiple states or later revisions matter. Keep image, text, controls and presentation frame independent. For working UI, use semantic controls rather than baked-in words and test the real component/data seam. For an image-only concept, coherent labels and states still matter, but behavior is untested.

Use [Mockup Image](../../mockup-image/SKILL.md) for imagery and its [generation contract](../../mockup-image/references/generation-contract.md) for actual image conditioning. Preserve native originals. Correct a text/layout issue in the text/layout source where possible instead of regenerating the photograph with the entire screen. Whole-image edits may be appropriate when requested or the composition itself changes; inspect unchanged regions for collateral degradation.

## Review from product scale outward

Open the screen without presentation hardware. Check the intended visual proposition, actual-script weight and line breaks, object associations, selection/detail/return continuity and relevant difficult inputs. Then review its board placement: natural proportions, readable scale and crop. The latter cannot rescue defects in the former.

For each material gap, record location/state → visible observation → effect → coherent repair → retest. Compare the output with relevant source pixels, not the prompt's promise. Keep craft, functionality, accessibility and owner preference separate. Required actions and correct dimensions cannot settle a rejection of the visual direction. If the content framing or expressive relationship still misses that brief, return to studies rather than treating clarity as sufficient approval.

Ordinary first drafts include inspection and refinement. Only an explicitly untouched evaluation uses [first pass](first-pass.md); preserve the first asset, inspect it before placement, then freeze the first complete screen before review. The optional [screen run](../templates/screen-run.json) checks declared file/hash/order evidence, not perception or visual quality. Deliver the artifact, key choices and honest untested limits, not a score or an asserted improvement from pack edits.
