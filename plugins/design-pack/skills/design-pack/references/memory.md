# Reusable learning and private project profiles

Keep three layers separate:

1. **Pack methods:** broadly applicable processes, conditional heuristics and verification practices. No user's identity, project details, private source links or visual tokens.
2. **Project profile:** approved or proposed colors, fonts, sizes, motifs, navigation, concepts, audience constraints and production specifications. Scope every entry to the project, artifact and date. Keep it outside this distributable package.
3. **Task evidence:** current observations, decisions, source versions, tests and remaining gaps. Evidence of one build is not a permanent design rule.

Read the applicable profile at task start and record that it was read. Merely installing a lens does not mean it influenced an assignment. Explicitly pass relevant context to another worker when delegation is authorized; do not presume invisible propagation.

## Resolve the requested writing style through the private profile

Before drafting or revising copy, inspect the applicable current brief and accessible project/user writing guidance. Prefer an explicit task instruction, then an explicit project voice, then the user's configured default for relevant work. A deliberate neutral choice is a real choice, not a missing value. When no preference is configured, use clear, context-appropriate provisional copy rather than inventing a named style or treating one client's voice as the pack default. This selection affects writing; it does not impose a neutral visual design.

Keep the concrete style guide, examples and project-specific phrases outside this package. Record the selected source/version, scope and any task override in the brief, then pass the relevant guidance to the actual maker. A profile path, installation or resolver result is not proof the maker read or applied it. If the required profile cannot be accessed, report the narrow gap; do not claim its style was used or silently substitute another named style. A low-risk provisional draft may proceed when permitted and clearly identified, but cannot close the requested-style requirement without review.

Translate style into the current copy's role, audience, language and truthful meaning rather than repeating slogans from examples. Preserve requested facts, product identity and action consequences. Compare actual rendered or delivered words with the selected guidance and current brief; reject generic stock phrases or style changes that obscure what the product does. Selecting a voice does not authorize sending, publishing or changing protected copy beyond the task. Configuration, actual guide consumption, generated wording and user approval remain separate evidence.

## Load applicable private fashion direction before production

For model or outfit generation, first locate the configured user/project fashion guidance through the current host's authorized profile or file-reading mechanism and read the actual relevant content before prompting. Use a known configured source, not a guessed location or a broad search for private files. If an authorized source points to a more specific current profile, follow that reference within its allowed scope. This skill supplies a procedure, not an automatic loader, background hook or credential/access grant.

Resolve overlapping values in the same order as writing guidance: explicit current task, then explicit project direction, then the relevant configured user default. Later corrections supersede earlier choices within their scope. A concrete current choice can override a saved default; an explicit absence of adornment or neutral styling is not missing data. Keep general preferences separate from one-character hair, garment color, age, pose and prop choices. Load only relevant fields and do not combine every past outfit into one person.

Record the source/version and what was actually read, applicable constraints, superseded choices and any unresolved values in the private brief. Distinguish source not configured, located but unread, successfully read, missing and access denied. When no profile is configured, use current task evidence without inventing a saved preference. When a requested profile is missing or access denied, report that narrow gap, do not retry through a bypass, and do not claim personal guidance was consumed. Independent permitted preparation may continue, but a required profile-read check remains not-tested until the actual source is read.

Translate the loaded details into current scene decisions: garment construction and wearing relationships, person/camera/lighting scope, supported variation and protected regions as relevant. Pass the specific allowed excerpt or accessible source to the maker, who must read it; a root-only summary or path does not establish downstream consumption. Retain the actual prompt/input and inspect the output separately. A receipt can record this read but cannot perform it or prove aesthetic fidelity. Do not copy the private profile, board links, character biography or user corrections into the public package, and do not claim fresh-session automatic integration without testing the real host flow.

## Promote a lesson carefully

For every candidate lesson, retain problem → context → intervention → observation → limitation. Ask whether it would remain useful for an unrelated client, medium and brand. Generalize the decision method, not the original aesthetic values.

Examples:

- Project request: a particular metallic title or illustrated motif. Reusable lesson: preserve approved identity while changing navigation; compare the reference's proportions and adapt to the target context.
- Project correction: a particular icon looks inconsistent. Reusable lesson: inspect family, weight, perspective and tone before imposing one visual treatment on every element.
- Project failure: the assistant said it used a saved guide but did not load it. Reusable lesson: record the specific guidance read and its effect on a decision; installation is not proof of use.

Do not retain specific names, values or source conversations in the public rule. Do not promote a single preference into an absolute rule. New general rules should identify when they apply and what would override them.

## Project profile fields

Use [project-profile.md](../templates/project-profile.md) outside the package. Record project identifier, scope, source reference, date, status (`user-stated`, `observed`, `proposed`, `confirmed`, `superseded`), decision authority and relevant values. Unknown measurements stay unknown. Older choices remain historical until checked against later decisions.

Before packaging or sharing, use an explicit file allowlist and inspect for private paths, personal identifiers, project assets, conversations, credentials and project tokens. Ignore rules are not a privacy guarantee. No task automatically publishes or migrates private profiles.
