# Mockup image

Make an image that belongs to its intended composition. An attractive standalone image can still fail its crop, obscure the product or compete with interface text. Apply this skill within [Design Pack](../design-pack/SKILL.md); it adds image production depth, not a second approval process.

1. **Identify the deliverable.** Image asset, image-only mockup, working interface containing an image, or prompt/brief? Record target frame, required crops, meaning, factual fidelity and available capability. Do not call a prompt a generated image or a screenshot a working UI. Generate only when the task asks for it; a pack/specification update is not such a request.
2. **Establish actual references.** Read only available and authorized material. A board URL, filename or remembered preference is not inspected image evidence. Record what was seen, unavailable, and permitted with the [image brief](templates/image-brief.md). Project references and identities stay in the project; do not publish personal boards/photos/names or infer sensitive traits. Viewing, provider submission and public reuse are separate uses. Reuse existing authorization without redundant permission questions; ask only for genuinely missing authority or essential material.
3. **Honor the requested medium, then choose direction.** If the user asks for a photograph or reference-based person photo, do not silently substitute illustration, SVG or another medium to avoid cost or missing access. Use an authorized available photo-generation route, or report the missing capability/reference while continuing independent planning. Medium alternatives are choices only when the brief leaves them open. Use [image-production.md](references/image-production.md) to compare photography, illustration, diagram, 3D or approved product assets. Select scene, framing, light and material language for the brief. Realistic, cinematic, graphic and tactile are different aims, not a quality ranking.
4. **Write the production brief.** Specify subject/action, required details, perspective, light, materials, crop anchors, protected regions, overlay space, exclusions, export and acceptance. Transfer only relationships supported by inspected references; do not copy an identity merely because a reference was mentioned.
5. **Produce within the chosen route.** Use the host's available image capability when authorized; no particular provider or installation is required. If only planning is possible, deliver the complete prompt/brief and state that no image was produced. Keep real interface text/buttons semantic and separate from the image, unless the deliverable is explicitly an image-only illustration/mockup.
6. **Inspect image and placement together.** Review anatomy/geometry, garment construction, light/material plausibility and artifacts, then actual crops, text contrast and control states. Separate factual and aesthetic judgments. Use [interface craft](../design-pack/references/interface-craft.md) for live state testing. Record observed checks and unavailable ones, not a taste score.
7. **Deliver.** Supply actual output or labeled prompt-only specification, intended placements, rights limits, available generation/edit history, alt-text guidance, crop/export instructions and defects. A seed/prompt does not guarantee reproducibility; photorealism does not prove a product property.

## Explicit first-pass override

For a fresh first attempt, [first-pass.md](../design-pack/references/first-pass.md) governs every step. Alternatives remain internal text planning; make one concept and freeze the first output before inspection. Do not generate variants and select a winner, regenerate failed hands, recrop after review or polish the supposed first artifact. Read-only views may inspect the frozen result. Failed generation or unavailable capability is reported; another pass needs separate authorization. Ordinary work may iterate within existing authorization.
