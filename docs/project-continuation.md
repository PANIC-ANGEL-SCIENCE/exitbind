# Continue an approved project direction

`project advance form --json` is the entry to source-grounded continuation.
It uses the existing Goal, Work and native host. Proposal inspection is read-only;
delegated execution requires an explicitly selected finite mandate.

A project direction describes an outcome and constraints. The native Lead
compares that direction with actual source, tests and accepted or in-progress
Work, then derives a useful bounded change. The operator does not need to write
every future ticket. Exitbind validates the selected sources and records the
resulting claim; the host supplies the Lead, workers and permissions.

## Prepare sources and a mandate

Use the host's already authorized Git or document tools to acquire only the
relevant material. An exported document is a declared snapshot, with its own
version and acquisition time. It is not a live connector observation.

`project advance form --json` describes the versioned specification and plan
fields. The specification includes a stable project and mandate identity,
explicit outcome and priority policy, approved source IDs, write and command
boundaries, roles, preservation conditions, expiry, finite Work/action/time and
concurrency bounds, and the external-publication decision. A document containing
imperative text supplies no additional authority.

Each source records its ID, kind, repository or exported identity, exact
revision, project-relative path, optional literal section locator, SHA256,
acquisition time, currentness classification and trust. `ownerDirection` identifies
an owner-designated direction; `reference` remains supporting data. Git sources
use an authorized local checkout, exact current HEAD and committed document
bytes. Exports use `declared_export`. All source reads must fit the configured
Lead's observe boundary. One observation is bounded to eight sources, 32 KiB per
source and 128 KiB total.

Keep derived specification and plan files in an approved ignored planning
directory. Changing a tracked plan while checking an earlier result would
change that result's tested input identity. Ignoring planning metadata does not
exclude product implementation or checkers from verification.

Run `project advance propose SPECIFICATION --json` to inspect the sources and
current project context. It creates no Work, child or hidden selection.
`propose` mode remains read-only; `cycle` permits one bounded task; `continue`
allows subsequent tasks inside the same finite mandate. A host records an
already authorized selection through `project advance select SPECIFICATION
--reason REASON --json`, reviews the preview and follows its exact apply argv.
That caller declaration does not authenticate a human or grant host permission.

## Derive a useful slice

Use the existing project Goal and named requirements to record agreed outcomes.
They describe the desired result, rather than an operator-supplied task list.
The Lead prepares a plan with a stable task ID, rationale, intended outcome,
acceptance and preservation conditions, exact cited sources, dependencies,
workflow, write scope, checker, resource estimate and explicit overlap judgment.
Configured recipients must fit both the task's write scope and the mandate's
command and role boundaries. Semantic overlap still needs Lead judgment; exact
IDs detect exact replay only.

Preview admission with `project advance admit SPECIFICATION --proposal PLAN
--json`, then use the returned apply argv. Admission reserves the exact task and
start intent before creating an ordinary Work. The existing Work owns its
checks, required separate review, Lead decision and receipt. Existing named Goal
coverage binds the requirements and checker before execution. The existing
preservation owner requires the combined preservation text to fit its 512-byte
limit.

If a response is lost, use `project advance status MANDATE_ID --json`. The same
task and contract resolve to the same Work even if the plan label changes.
Different task content under an existing identity refuses. A reserved but
missing or uncertain Work remains held; changing its name is not recovery.
If the exact start exists but its admission observation was lost, use the
claim's `savedStartRecovery` preview and exact apply form. It verifies the
committed start and repairs accounting only, including after a stop; a missing
or different start never triggers another start. Preview stays read-only.
The same preview lists exact committed Lead/reviewer, review-policy and governor
decision receipts whose observation was lost. Apply verifies those canonical
events again and observes their original debits; it never repeats a decision.

Consume the existing complete Work assignment and its exact action forms
through the native host. After current checks, independent review and Lead
acceptance, inspect the changed project and choose the next useful slice under
the same mandate. Do not mark a source checkbox complete from a child reply.
Current input/check evidence and historical acceptance remain distinct.
External documents stay unchanged; the status is local derived progress.

## Stop and learn

`project advance stop MANDATE_ID --reason REASON --json` records a stop and
requests actual host interruption/readback for owned running children. A stop
record is not evidence that a process terminated. Safe inspection and saved
result recovery must remain available. A real owner-selected revision retains
previous claims and the original elapsed-time origin.

Admission, each native launch or retry, mutation grant, managed file effect,
observed check, pre-return check, recorded review/Lead decision and successor
debit one actual action unit before execution. Estimates remain planning advice.
Failed and unknown attempts stay spent; changing an operation or plan label
does not reset authority. Exact verified saved-result recovery makes no fresh
effect and no new debit. An unknown effect remains held until its owner proves
the original identity and result; it is never replaced by a blind retry.

The frozen Work association binds project, mandate revision, source digest,
task and claim root. Successors retain that association and the original account
and elapsed origin. A stopped or changed source, configuration or selected
memory blocks new controlled effects. Owned native and checker waits poll for
revocation and request bounded interruption. Inspect the actual process/group
observations before claiming termination. Native tools still obey the host's
permissions; these controls do not create an operating-system sandbox or an
external publication adapter. Source documents are not rewritten by this route.

An older executable that does not recognize the frozen association refuses
these Work ledgers. Resume them with a supporting executable; preserve previous
binaries and ordinary Work rather than editing the ledger to downgrade it.

For an observed mistake, first inspect relevant existing skills and lessons.
Prefer a causal parser, form or check correction for a deterministic error. A
reusable procedure stays inactive until original and different trials, a
misleading-use negative, independent review and exact-byte promotion pass the
existing memory lifecycle. Verify delivery and useful use in a fresh relevant
task, exclusion in an unrelated task, and expiry/revocation. Stored, received,
used and improved are separate observations; one reuse does not establish a
general quality or economic gain.
