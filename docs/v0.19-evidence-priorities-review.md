# v0.19 Evidence Priorities Review

This note reviews the evidence and product-priority implications of the v0.19
mechanism as it exists on the current public line. It is not a new product
contract, benchmark result, or claim of competitive exclusivity.

This review predates the 0.23.1-rc.1 line. Later releases change update, install,
host integration, and presentation behavior; they do not change the
checked-run, tested-input, residual-packet, or stale-evidence semantics of the
0.19 minor line described here.

## What v0.19 actually adds

The strongest v0.19 distinction is narrower than generic false-completion
prevention.

A check can genuinely pass and still be unusable for the result that is now in
front of the agent. The same applies to a review approval. v0.19 binds checks,
review approval, and final acceptance to the applicable checked-run state and,
for v6 runs, to the tested-input identity.

A useful summary is:

> A result may reuse evidence only while Exitbind can establish that the
> evidence still belongs to that result.

This is different from merely recording that a command once exited successfully.

The public README should keep this distinction, but it should not turn it into a
claim that no other system can represent stale evidence or stale approval.
Competitive uniqueness requires a separate, current comparison.

## Important correction: stale-evidence behavior is already tested

The repository does not lack stale-evidence regression coverage.

In `tests/subject_progress.rs`,
`source_or_checker_edit_without_new_submission_invalidates_reuse_and_acceptance`
already exercises a strong case:

1. functional and preservation checks become current;
2. review becomes current;
3. a source file or preservation checker changes without a new worker
   submission;
4. the previous packet is no longer reusable;
5. the relevant checks execute again;
6. the previous review is not reused;
7. low-level acceptance with stale evidence is refused;
8. a fresh review and acceptance path is required.

The test also uses execution counters, so the unchanged and changed cases are
not inferred only from packet labels.

Likewise, packet validation and preservation gating have focused regression
coverage, including malformed/unsupported packet handling and refusal of
preservation configuration without the required functional check policy.

The implementation gap is therefore not "build stale-evidence protection from
scratch."

## The public-proof gap is real

The stronger criticism is that the registered public proof surface has not
caught up with the v0.19 mechanism.

`proof/claims.json` currently registers
`CLAIM-CHECKED-ACCEPTANCE-001` against `false-completion-v1`. That scenario
demonstrates refusal and recovery for missing/failed checked evidence. It does
not directly demonstrate the more distinctive v0.19 case:

> a previously passing check becomes stale after a relevant result/input change.

This creates a mismatch between the strongest mechanism now implemented and the
first reproducible proof a prospective user is shown.

The next proof work should therefore promote an existing invariant into a
small installed-binary scenario rather than invent another subsystem.

A useful scenario should demonstrate, with observable command counts:

- unchanged applicable inputs after a fresh process/session boundary: no
  unnecessary re-check or re-review;
- a relevant source or checker change: old evidence becomes inapplicable and
  the required check really executes again;
- a review that belongs to earlier tested inputs: passing checks alone do not
  authorize acceptance.

The scenario should register a new scoped claim instead of rewriting the
historical `false-completion-v1` result.

## The earlier workload comparison already included a changed-input resume

The published
`docs/holytail-workload-findings.md` should not be reinterpreted as though it
lacked a resume/change condition.

That comparison explicitly included a fresh-context resumption after an input
change introduced after the first worker result and review. Both the native
baseline and the Soulmate condition detected the new broken link and repaired
it. The report therefore supports a stricter conclusion:

- the tested native baseline was already competent;
- both conditions reached the correct product result;
- the Soulmate condition added structured bindings and operations;
- no quality or reconstruction advantage was observed in that small sample;
- directly attributable token slices did not establish overall token savings.

This is useful negative evidence. It should not be explained away as a missing
condition merely because v0.19 now has a stronger mechanism.

A new v0.19 comparison is justified, but it should be a new experiment with a
new preregistered question rather than a retrospective rewrite of the old one.

## A wrong door does not require multiple rework cycles

Stale evidence can occur within one task and one session:

```text
check passes on A
-> a relevant file changes
-> current result is B
-> evidence from A is presented as if it applies to B
```

Multiple sessions, handoffs, and rework cycles may increase the opportunity for
this failure, but they are not prerequisites.

The product hypothesis should therefore be framed around evidence applicability,
not around a required number of attempts or sessions.

## The next real product question

The highest-value question is no longer whether Exitbind can mechanically
reject stale evidence. v0.19 already has meaningful deterministic coverage for
that behavior.

The next question is:

> In workflows where a strong native agent/harness is already competent, does
> Exitbind reduce the total cost of reaching one independently verified accepted
> result, prevent a failure the baseline actually makes, or both?

A fair comparison should keep the baseline strong. Do not design the baseline
to merge stale evidence by assumption.

Useful measurements include:

- independently verified final correctness;
- false acceptance;
- unnecessary refusal/blocking;
- actual check executions;
- review requests;
- frontier-model calls and attributable tokens where measurable;
- rework;
- user interventions;
- elapsed time with waiting distinguished where possible;
- setup and recurring operational cost.

If both paths are correct and Exitbind costs more, that is a valid negative
result for that condition. If the native path also detects the stale evidence,
the useful question becomes whether Exitbind reaches the same safe outcome with
less reconstruction or fewer repeated actions.

## README and packaging are secondary, not irrelevant

The README can still be improved: repeated descriptions of the exit stages can
be collapsed, and optional presentation such as Neuro can move deeper in the
documentation.

Those edits reduce adoption/comprehension cost, but they do not substitute for
a stronger public mechanism proof or a fair workflow comparison.

Compatibility paths should not be moved merely because an old product name is
visible at the repository root. A compatibility move is a product/migration
change, not just copy editing, and should be justified by an actual user-facing
problem.

Similarly, package metadata, additional platform builds, or new distribution
surfaces should be prioritized from observed adoption friction rather than
treated as a generic completeness checklist.

## Recommended order

1. Add one public, installed-binary stale-evidence/reuse scenario using the
   existing v0.19 mechanism and observable execution counts.
2. Register the new scoped claim without changing historical proof bytes.
3. Run one small, predeclared v0.19 comparison against a competent native
   workflow.
4. Publish positive, neutral, or negative results without weakening the
   baseline or changing the stop rule after seeing outcomes.
5. Then simplify README duplication and optional presentation.
6. Add packaging/distribution breadth only where observed user friction
   justifies it.

The immediate opportunity is not another large feature. It is to make the
strongest behavior already present in v0.19 easy to reproduce, then test whether
that behavior produces user-visible value against a strong baseline.
